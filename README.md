### 2단계 요구사항 - 모바일 앱 요청에서도 로그인 유지하기
선택 도구: 세션
다른 후보: 토큰
선택 이유: 현재 세션 방식의 로그인이 구현되어있는데, 최대한 변경을 최소화해서 로그인 기능을 구현해보고 싶었습니다.
불편하거나 아쉬운 점: 우선 모바일을 추가하면서 CORS 설정이 필요했다. 근데 같은 기기여서 그런지 실제로는 Cors 설정이 걸리지 않아서 아쉬웠다. 실제 모바일 기기에서 해보고 싶다.

완료 기준    
- [x] 모바일 앱 요청에서도 로그인한 사용자를 식별할 수 있다.
- [x] 인증 정보가 없거나 유효하지 않은 모바일 요청을 거부한다.
- [x] 선택한 인증 방식과 다른 후보를 비교해 설명했다.
- [x] 웹 인증 흐름과 모바일 인증 흐름의 공통점과 차이점을 설명했다.


### 3단계 요구사항 - 인가: 자기 매장 예약만 관리하기
- [x] 매장 테이블 추가 : Store - id, name, member_id
- [x] Member에 권한 추가하기 : Role
- [x] 관리자 API 권한 검사 기능 추가
- [x] 관리자 예약 수정 및 삭제 API 추가

완료 기준    
- [x] 매장 매니저는 자기 매장의 예약만 관리할 수 있다.
- [x] 다른 매장 예약에 접근하는 요청은 거부된다.
- [x] 인증 실패와 인가 실패가 구분된다.
- [x] 인가 판단 위치와 선택 이유를 설명했다.

선택 도구: Interceptor에서 공통 인가 처리 + Service에서 추가적인 인가 처리   
다른 후보: Service에서 validateRole와 같이 권한 처리를 한다.    
선택 이유: admin와 user 클래스를 이미 분리한 상태에서, admin 클래스들에 대한 공통적인 인가 처리를 하고 싶었습니다.   
그래서 1차적으로 admin url은 접근하는 사용자가 관리자일 때만 사용하도록 공통 인가 처리를 구현헀습니다.   
이후 매장 주인인지와 같은 세부적인 권한 검증은 Service에서 추가로 했습니다.   
인가 판단 위치:  AuthorizationInterceptor를 구현해서 Controller전에 한번 하고, Service에서 세부적인 판단을 했습니다.  
유지하거나 변경하고 싶은 점: admin Url은 amdin 일때만 호출할 수 있도록 하는 것은 유지하고 싶습니다.

-> Admin 공통의 관심사라고 생각해서 Interceptor에서 처리하도록 분리했습니다.

